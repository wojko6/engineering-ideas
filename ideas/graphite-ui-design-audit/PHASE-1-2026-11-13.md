## Candidate A.1 — bookmark tooltip label preservation (not deployed)

Operator-provided `findersidebar.cpp` excerpts confirmed the following source behavior, without guessing Qt runtime behavior:

- The custom `SidebarDelegate` uses `QFontMetrics` elision with the Qt `ElideRight` setting to shorten long labels.
- During `FinderSidebar` model rebuilding, ordinary locations set their tooltip to a filesystem path or display URL via `item->setToolTip(...)`. Thus a renamed bookmark's full **display label** is not guaranteed to appear in the tooltip, even though the path remains available.
- Cloud activity status tooltips are separately refreshed in `updateCloud()`; do not overwrite them.
- The alpha values and visible selection shapes have not been shown to cause an accessibility defect; do not alter the paint colors without operator observation.

An **offline, one-source-file A.1 candidate generator** was prepared, and its synthetic fixture / negative-guard self-test passed. It is intentionally not a change to this GitHub repository's operational Finder source. It checks the known `findersidebar.cpp` SHA-256 `e06a302b075d0173aa559334016a6bd29f0e11b5de5d3bc512f57ccbba980a58` in both original and copied A source trees, plus the opaque Graphite A chrome marker. It creates only a separate `graphite-v05-A1-tooltip-candidate` containing one revised C++ file and a narrow unified diff. The change adds the original full display label above the existing location detail, unless they are identical. Cloud tooltips, chrome, accent, selection and paint are untouched.

**Verification status:** generator fixture PASS; operator preflight NOT RUN; patch creation NOT RUN; native build NOT RUN; GUI acceptance NOT RUN; original v0.5 A remains the selected visual reference. Do not deploy or merge A.1 without an isolated operator run.

## Visual follow-up — duplicate navigation docks and search-toolbar styling

At the 2026-11-13 operator-run **isolated A.1** visual checkpoint, three screenshots expose two issues not captured by the original matte-background acceptance:

1. **Duplicate left navigation docks.** The top section is the inherited expandable folder-tree dock; the bottom section is the custom Finder sidebar (Recents, Favorites, cloud and Locations). Existing local source previously showed distinct `foldersDock` and `placesDock` construction and installation of custom `FinderSidebar` into the latter. Both were simultaneously visible in the GUI. This is not a second instance of the same widget and is separate from the fixed matte background. Review default dock visibility and saved-state restoration: present custom Finder sidebar by default, keep the Folder Tree opt-in through the existing Panels action, and do **not** override an explicit saved preference.
2. **Search controls do not share the Graphite visual language.** The newly displayed search row contains a search input, a filter action and close control; below it are scope options ('Stąd' / 'Wszędzie'). The operator notes mismatched control height, spacing, border and focus/selection treatment. Limit any change to the search UI selectors/widgets, preserving P0-A/P0-B2 search behavior, compact progress, keyboard focus and Polish labels. Do not broadly style all Qt controls.
3. **Tooltip acceptance is still open.** The screenshots show sidebar and search/navigation states, not a visible tooltip for an elided label. A.1's patch was built successfully, but these screenshots alone do not verify tooltip text or cloud-status regressions.

Next evidence: inspect the exact folder-dock initialization/restore code and search-bar creation/object names in the operator's local source. Any fixes should be separate, incremental, reproducible local build candidates **after** the v0.5 A.1 baseline, with no changes to the live launcher or system Dolphin.
