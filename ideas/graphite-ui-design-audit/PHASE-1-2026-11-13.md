## Candidate A.1 — bookmark tooltip label preservation (not deployed)

Operator-provided `findersidebar.cpp` excerpts confirmed the following source behavior, without guessing Qt runtime behavior:

- The custom `SidebarDelegate` uses `QFontMetrics(font).elidedText(..., Qt::ElideRight, ...)` to shorten long labels.
- During `FinderSidebar` model rebuilding, ordinary locations set their tooltip to a filesystem path or display URL via `item->setToolTip(...)`. Thus a renamed bookmark's full **display label** is not guaranteed to appear in the tooltip, even though the path remains available.
- Cloud activity status tooltips are separately refreshed in `updateCloud()`; do not overwrite them.
- The alpha values and visible selection shapes have not been shown to cause an accessibility defect; do not alter the paint colors without operator observation.

An **offline, one-source-file A.1 candidate generator** was prepared, and its synthetic fixture / negative-guard self-test passed. It is intentionally not a change to this GitHub repository's operational Finder source. It checks the known `findersidebar.cpp` SHA-256 `e06a302b075d0173aa559334016a6bd29f0e11b5de5d3bc512f57ccbba980a58` in both original and copied A source trees, plus the opaque Graphite A chrome marker. It creates only a separate `graphite-v05-A1-tooltip-candidate` containing one revised C++ file and a narrow unified diff. The change adds the original full display label above the existing location detail, unless they are identical. Cloud tooltips, chrome, accent, selection and paint are untouched.
