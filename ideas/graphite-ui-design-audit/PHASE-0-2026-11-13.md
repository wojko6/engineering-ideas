## Proposed five-part visual direction

1. **Product:** a capable local KDE file manager with Finder-inspired interactions and familiar native behavior.
2. **Character:** calm, precise, ordered.
3. **Material:** neutral charcoal and restrained matte layers; not a generic glowing AI dashboard.
4. **Meaningful moments:** file content, icon semantics, operation progress, selection, and keyboard focus.
5. **Signature:** a consistent sidebar → file list → information pane depth hierarchy, including properties and dialogs.

A **synthetic, independent** offline HTML example contrasts historic violet values with a candidate graphite ramp: sidebar `#111315`, window `#17191B`, surface `#202326`, selection `#394046`, primary text `#EEF1F3`, secondary text `#BDC5CB`, focus `#DCE3E7`. The mockup contains no real filesystem data and makes no Qt compatibility claim. Static color contrast checks measured **15.54:1** for primary/window, **10.08:1** for secondary/window and **9.28:1** for primary/selected. These are only selected WCAG-style contrast ratios for candidate RGB pairs.

## Phase 0 update — actual visible sidebar rendering chain

Read-only operator inspection of the current local Finder source (not the standard KDE places panel) established:

1. `DolphinMainWindow` creates `PlacesPanel` but hides it and installs **`FinderSidebar`** into the places dock. Earlier focus on the inherited `KFilePlacesView` was therefore not an explanation for the visible custom sidebar.
2. `FinderSidebar : QListView` has a transparent background and viewport plus its own local QSS. It paints neutral white-alpha hover/selection directly in a custom delegate, while **four** `finderAccent()` references tint icons and drag/drop indicators.
3. `finderAccent()` reads `kdeglobals` `General/AccentColor` with `QPalette::Accent` fallback. No runtime measurement of the actual accent RGB was made.
4. `FinderChrome::paintBackground()` paints the sidebar strip with `SidebarColor(44,44,48,200)` using `QPainter::CompositionMode_Source`, making the strip translucent and visually affected by its backdrop. **This is the confirmed rendering owner** of the sidebar's background; the complete perceived-violet attribution still requires a GUI check.
5. The operator-reported v1.9 launcher still referenced an older `finder-menu-tahoe-kde-v15-progress-p0b01.qss`, not the scanned Charcoal v0.4. No Finder process was detected by the particular process search at that moment. Distinguish candidate QSS from active runtime appearance.

A **separate operator-only v0.5 LAB bundle** has been built but **not deployed or applied**. It produces fresh isolated copies and strict patch diffs, with two orthogonal experiment variants: (A) change only sidebar strip to opaque neutral RGB(26,26,26), and (B) A plus replace four custom-sidebar `finderAccent()` calls with a sidebar-local steel-blue RGB(143,160,175). The generator fails closed on unknown source revisions and has no live `--apply` or `--build` function. Its self-tests and a synthetic end-to-end preparation/verification test passed; actual Fedora source preflight, native build, GUI and functional acceptance remain **PENDING**.

**Risk note:** the opaque A/B strip intentionally sacrifices the glass/translucency effect and is diagnostic rather than an accepted aesthetic final. No global accent helper, production system settings, stock Dolphin, active Finder source or launcher should be changed before isolated review.
